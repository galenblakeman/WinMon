## Signed setup and Settings increment

Implemented `WinMon.NetworkSetup` and its NUnit project, added both to the solution and `Verify.ps1`, and integrated opt-in collection into Settings and MainWindow. The feature defaults off. Toggling and cancelling Settings invokes no provisioning. Save first attempts the already-authorized compatible service without UAC; otherwise an explicitly initiated enable/repair verifies and launches the signed helper with `runas`. The preference becomes enabled only after the original unelevated client subscribes and reads a healthy snapshot (warming up is healthy). Startup never provisions or elevates. Disabling releases only the current subscription; shared installation/authorization remain. Collection remains independent of Connections visibility, minimize and tray state. Store builds never invoke service/setup and reject embedding a bundle.

The bundle contains fixed-name NativeAOT helper, service ZIP and detached RSA-signed manifest, embedded into the app before app signing. Runtime validation checks the existing release public key, exact app version/runtime/protocol, decoded SHA-256 hashes, sizes and Authenticode/publisher. Helper/archive handles deny write/delete throughout launch and handshake. No unsigned-development fallback exists. A standalone native helper avoids loading writable staged managed dependencies under elevation.

The random local first-instance setup pipe rejects remote clients. Its protected DACL grants the requester full server rights and administrators/System data rights, excluding instance creation. The app authenticates the launched helper PID with a held process handle; the elevated helper authenticates the actual pipe-server process and obtains its token SID, including alternate-account UAC. No command-line/request SID or install path is accepted. The 4 KiB source-generated wire uses ready/commit/complete, nonce/version checks, bounded timeouts and disconnect rollback. The original client verifies subscription/health before acknowledging installation.

Deployment uses a checked Program Files parent, exclusive maintenance file lease, bounded ZIP extraction, protected staging, exact own-process/LocalSystem/demand-start/quoted-path SCM identity, authorized SIDs limited to service query-configuration/query-status/start mask `0x15`, independent uninstall registration and an administrator-protected owned-file inventory. Existing files/policy, running state and DACL are captured before mutation; failed install/health/commit restores them. Removal refuses unknown files/directories, affects all users only after explicit confirmation, and preserves ordinary app preferences. The installed helper's self-removal can require reboot (3010). Removal is irreversible after commit: an OS failure during deletion can leave protected files or a deletion-pending service for administrator repair. A failed cleanup after an acknowledged install retains protected backup files rather than reverting a healthy installation. Machine crash/power-loss recovery across a directory swap still requires native acceptance; rollback tests cover managed failure/disconnect paths, not crash consistency.
