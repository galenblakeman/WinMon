# WinMon developer guide

MCP `sample_performance` uses `UsageLedger.IsValid` before interpreting an absent process lifetime as no longer observed. An empty inventory from failed Windows CPU collection does not end the requested recording; gaps remain excluded, while valid independent process inventories can still establish absence. `ProcessImagePathProvider` retains successful paths for the observed lifetime and retries empty direct/fallback results after 30 monotonic seconds. PID-only fallback results still wait for a later matching lifetime snapshot. An instance-local `TimeProvider` controls retry boundaries in tests; disappeared lifetimes drop their cache and retry state. See [sampling recovery corrections](design/SAMPLING-RECOVERY-CORRECTIONS.md).

ReSharper uses the shared `WinMon.sln.DotSettings` syntax policy and dictionary. Keep correctness inspections enabled and explain intentional exceptions beside the source. The [inspection review](INSPECTION-REVIEW.md) records the disposition of the November 8, 2026 report.

`SelectedActivityTab` persists the last activity tab (Processes=0, Services=1, Usage=2, Connections=3). Missing or invalid values select Processes. Startup restores the tab after loading view preferences, suppressing the usual tab-selection expansion so the saved collapsed state is preserved. Tab changes use the existing exit-save path.

Services persists `ServiceSortColumn` (CPU=0, memory=1, I/O=2, name=3), `ServiceStatusFilter` (all=0, running=1, stopped=2) and `ServiceIncludeWorkers`. Missing keys retain CPU/all/workers enabled. Name sort is valid only with Top set to All (0). Startup restores these controls after Top, suppressing change events while restoring; user filter changes update the immutable preferences saved through the normal exit path.

## Requirements

- Windows x64.
- The portable `MonCore` project and `MonCore.Tests` target plain `net10.0`; they can also build and run on macOS with the .NET 10 SDK. That macOS run is a separate verification step.
- The .NET SDK pinned in [global.json](../global.json) (10.0.402, latest-patch roll-forward).
- An interactive desktop session for the smoke modes and the benchmark, which open real windows.

## Build and test

The solution also includes `src/WinMon.Mcp` and `tests/WinMon.Mcp.Tests`, using ModelContextProtocol 2.4.0 and Microsoft.Extensions.Hosting 10.0.15. Normal verification explicitly runs the MCP suite. The Windows stdio host registers fourteen read-only tools and one singleton `SamplingOwner`; no SDK or hosting dependencies enter MonCore. `MonitorSession` owns native collection at one second, with an inline serialized drain and 120 retained published frames. Requests read immutable frames and never touch collectors. MCP DTOs apply lifetime identity, privacy allowlists, availability, input bounds and a 256 KiB serialized-result limit. See [MCP setup](MCP.md) for commands, units, freshness, weighted aggregation and limits, and [implementation acceptance](design/MCP-IMPLEMENTATION.md) for current evidence.

The solution builds `src/WinMon.Cli` and `tests/WinMon.Cli.Tests`; normal verification includes the CLI suite. The CLI references MonCore.Windows/MonCore, Spectre.Console 0.57.2 and System.CommandLine 2.0.15. No terminal dependencies enter MonCore, and the CLI never references WPF. CLI resources link the existing ten translated `.resx` files and generated properties with a console-only culture accessor. Its project defines the assembly title and description and emits repository/license metadata; version, company, author and copyright come from `Directory.Build.props`.

`WinMon.Cli snapshot` captures a baseline, waits one second with cancellation, then captures a measured frame through `WindowsFrameSource`. It ranks only that interval. JSON has an explicit versioned raw-unit report schema; unavailable readings remain null. Terminal output treats observed strings literally and removes control/format characters. `TerminalText.Fit` uses Spectre cell-width truncation, including CJK/surrogate boundaries; detail tabs become spaces.

Standalone connection reports index observed Windows process lifetimes once, resolve endpoint owners once and sort matching endpoints once. The matching count is captured before `--top` limits JSON/table projection, preserving stable tie order and truncation metadata without formatting discarded endpoints. Archived Usage cells and details always show the recorded local date/time; live and frozen session Usage retain their sample-relative “now” label. See [the CLI report corrections](design/CLI-REPORT-CORRECTIONS.md).

The CLI assembly and executable are named `WinMon.Cli`. Release configuration mirrors WinMon: a default `win-x64` runtime identifier, self-contained deployment, single-file publishing, uncompressed assemblies, native-library self-extraction, optimization and embedded symbols. `dotnet publish src/WinMon.Cli/WinMon.Cli.csproj -c Release -m:1 -p:UseSharedCompilation=false` writes `src/WinMon.Cli/bin/Release/net10.0-windows/win-x64/publish/WinMon.Cli.exe`. Debug retains the framework-dependent development build.

`watch` runs one Spectre live renderer/input owner on the alternate screen. MonitorSession owns native sampling, queues and history; its post delegate enqueues callbacks drained by that terminal owner. Input is polled every 50 ms, with repaint only on samples, keys, health or size changes. The async command yields before entering the loop so System.CommandLine can install signal cancellation. Shutdown closes the session, cancels/awaits sampling and optional traffic, then disposes the traffic client. Spectre restores the previous screen/cursor even if rendering throws. The CLI caps the gen0 budget at 6 MiB like the desktop app, which keeps `watch` near 52 MiB of private bytes instead of about 80 ([history](PERFORMANCE-HISTORY.md#cli-whole-process-profile-and-gen0-cap-november-10-2026)).

Program sets non-redirected output to BOM-free UTF-8 before creating commands or capturing Console.Out, and restores the previous encoding in finally. Spectre.Console 0.57.2 derives Unicode capability from the output encoding; an inherited OEM code page otherwise selects ASCII gauges/history despite a capable terminal/font. Redirected output is not reconfigured. Input encoding and Unicode capability overrides are unchanged.

TerminalChrome defines the fixed CLI palette: bright-cyan #00D8DB key names, brackets and sort digits; orange CPU #FD6C0F, blue memory #1195FD, yellow disk #FCEA1D, orchid network #DC77FB and turquoise GPU #00F2C3. Active-tab keycaps keep the cyan foreground on the existing selection background. TerminalCharts renders literal styled spans for current values, bars and resource history, with neutral panel borders/captions. Compact and numeric summaries use the same mapping, including disk/network throughput. Spectre performs color-depth conversion and suppresses foreground colors for no-color output. Cell-width clipping and text remain identical across color modes; CLI colors do not read WPF preferences.

`InteractiveState` keeps separate controls, selection, details and session pins for Processes/Services/Usage/Connections. Stable keys include executable identity or PID plus creation token. Generic tables carry plain columns and row observations with deferred, cached cell/detail formatting. The renderer fits one line per row, selects columns to fit the terminal, automatically reveals the sort metric and supports horizontal detail panning. Numeric watch columns and their headings align right; names, Services status and Usage last activity retain their existing alignment. Hidden columns add a localized Left/Right hint to the status line. The filter line is rendered only while a filter is edited or set, and `InteractiveMonitor.PageSize` gives that row back to the table otherwise. `BuildTable` composes padded lines itself: a 2-cell marker, a name column that takes the spare width (22 to 40 cells) and 13-cell value columns; headings carry the digit of the key that sorts by them (`KeyColumn`). Blank lines after the table keep status, warning and key hints at the bottom, leaving the last terminal row free. Active tabs have a text marker independent of color. Detail tabs become two spaces before sanitization and horizontal panning. No WPF controls are linked. Below 80×20 it shows resize guidance and still accepts keys.

Processes uses ProcessRanking/ProcessSearch/ProcessPins directly, replacing the newest compacted sample with LatestFull through SampleList. CPU/I/O use the default five-second gap-aware window, GPU readable intervals, memory/counts the latest sample. Finite Top omits inactive rows unless searching; All includes them. Pins get independent inclusive ranking and missing-data state, so reused PIDs cannot inherit readings. Retention options are immutable snapshots published to the worker; finite Process Top permits compaction while retaining pins/selection, and All retains every process subject to the core budgets. History is bounded to 1,800 seconds/500,000 process entries, connections to their existing entry budget and services to 120 seconds. Usage consumes full live samples regardless of process-history compaction.

CLI interactive and text-snapshot headers include the assembly informational version, read once from the metadata generated from Directory.Build.props. The CLI reuses the selected frame and retained process history without changing sampling or retention. At the 120x24 minimum for the wide layout, five 23-cell panels plus four gaps occupy 119 cells in CPU/Memory/Disk/Network/GPU order, with 19-cell resource bars/histories. Colored titles match primary values: percentages for CPU/memory/disk/GPU and download throughput for network. The former spacer row contains CPU clock, used/total RAM GiB, disk MB/s, upload rate and GPU memory/3D. GaugeReadoutText is shared with desktop through linked portable source. NetworkChartScale in MonCore supplies the same busier-direction, 1-2-5 rate scale used by CpuGraph, with a 1 Mbps floor; CLI download bars/history normalize against the current adapter over the displayed 60-second window and label the physical maximum. This does not depend on link speed; desktop can use its separately configured gauge-peak window. Other resource histories keep a 0-100% scale, and volume/adapter changes break their traces. Missing readings stay unavailable. The wide summary is seven lines; the former separate disk/network detail rows are removed and paging reclaims those two rows. Compact/minimum layouts retain detail rows and their height, using network download units. Pause uses frozen frame/history for values and scales. Interactive table metric cells display localized Unavailable values as the existing MissingReading dash; gauges, details and snapshot data keep their original labels. Processes use numeric columns without a History column or process-history footer; removing these reclaims horizontal space and one table row. The CLI no longer links ProcessGraphData; desktop process graphs are unchanged. Narrow layouts retain column panning.

ServicesTab uses ServiceRanking and the desktop's status/search/order rules; worker details show the host and observed descendants with window-ranked metrics. UsageQuery in MonCore now supplies both WPF UsageView.Visible and UsageTab, retaining exact filtering, ordering and tie-breaking. CPU Share uses Usage.MachineBusyTicks, and recent activity uses the selected latest timestamp for the desktop's Now label. ConnectionQuery groups endpoint lifetimes/executables and uses ConnectionTrafficTotals for requested periods, preserving missing/incomplete/discontinuous data. Unknown-owner ordering receives the localized label from the caller.

Optional `--network` runs NetworkTrafficClient through the existing authenticated NetworkServiceClient. Monitoring only connects/subscribes to an installed service. Explicit `network start` checks an installed service; `network install` uses a linked compilation of the desktop NetworkSetupBroker, preserving signed-package verification, requester identity, UAC, health verification and rollback. `NetworkServiceBundleDirectory` embeds the same four signed assets as the desktop. Missing bundles fail before launching anything; Store builds define WINMON_STORE and reject setup. Setup success means the service is reachable, not that complete rates are available, and does not persist desktop settings. A volatile TrafficSample supplies one stable client SessionId and the latest snapshot to SamplingOptions. Service failures publish a null gap, dispose the failed connection and retry after five seconds. Protocol mismatch stops with UpdateRequired; connect/subscribe/snapshot operations have bounded cancellation. The public client's disposal cancels and awaits active connection cleanup. Pause retains immutable resource/service/usage/connection snapshots and sampling/traffic health while live collection continues.

TerminalChrome applies styles to literal Paragraph segments, never interpreting process or endpoint text as Spectre markup. Toggle markers use [✓]/[ ] with Unicode and [x]/[ ] otherwise; checked markers retain green styling. Key names use soft cyan #7DCFFF inside Titanium #8795A5 brackets, with GitHub Dark #264F78/#E6EDF3 for selection/active-tab background and text, green #3FB950, gold #D29922 and red #FF7B72 for semantic status. CliSettingsStore owns versioned, bounded JSON at LocalApplicationData/WinMon/cli-settings.json, independently of WPF preferences. It validates controls and executable/service pin identities, retains malformed JSON before replacement, and refuses to overwrite unknown versions. A per-path named mutex serializes read/merge/write across CLI processes; a unique same-directory temporary file is flushed and moved atomically. CliSettingsSession captures controls after keys, debounces changes for 500 ms and flushes on exit. It merges only fields changed from the effective startup state, so temporary arguments cannot leak into saved defaults. Pin additions/removals merge by stable identity. No settings serialization runs on normal sample deliveries; --no-save omits the saving session. Explicit option detection uses System.CommandLine OptionResult.Implicit, including false boolean arguments. Snapshot commands do not read or write these preferences. settings set --network changes a preference only; monitoring retains the existing service authorization checks. CLI display units link the desktop TableMetricText and RateText implementations. Fixed-unit column headings and suffixes are removed. Missing readings and snapshot JSON raw units/schema are preserved; only display strings change. `dotnet build` output is at `src/WinMon/bin/Release/net10.0-windows/win-x64/WinMon.exe`, and `dotnet publish` writes the single-file distribution to `…/win-x64/publish/WinMon.exe`. Release builds are self-contained, optimized and embed their debug symbols. Two settings in `WinMon.csproj` are measured choices; the [performance history](PERFORMANCE-HISTORY.md#allocation-gc-and-compression-october-20-2026) has the numbers:

- **Single-file compression is off.** Compressed assemblies are inflated into private memory instead of mapped from the file, which roughly doubled the working set and slowed startup, in exchange for an executable about 90 MB smaller.
- **The GC gen0 budget is capped at 6 MiB** (`System.GC.Gen0MaxBudget`), in every configuration. Workstation GC sizes gen0 from the L3 cache, and at WinMon's allocation rate the app committed the whole budget between rare collections. The setting is undocumented, so confirm with `GC.GetConfigurationVariables()` that it still applies after a runtime upgrade.

## Verify a change

```powershell
./tools/Verify.ps1                                # build (app, tests, benchmark) and run the tests
./tools/Verify.ps1 -TestScope Unit                 # tests without Integration or Elevated categories
./tools/Verify.ps1 -TestScope Integration          # only Integration-category tests
./tools/Verify.ps1 -Smoke feature, services       # also run those smoke modes
./tools/Verify.ps1 -Smoke all -Store              # every smoke mode, against the Store variant
```

The script builds into `artifacts/verify/build` (or `build-store`), so it leaves your normal `bin` folders alone. Each run has a unique desktop/store timestamp folder under `artifacts/verify/`; it contains one TRX result per test project. It discovers `tests/**/*.Tests.csproj` and fails if any is absent from the solution. Each result line reports passed, failed, not-executed and unexpected totals; missing/malformed reports, inconsistent counters, aborted runs and unexpected skips fail verification. Expected opt-in, build-variant and environment skips are listed by exact project, test name and reason in `tools/TestResults.ps1`; update that list only when the skip is intentional. `tools/Test-Verification.ps1` checks these rules before each build and can also run alone.

`-TestFilter` accepts a normal `dotnet test --filter` expression and combines it with `-TestScope`; all scopes force `NUnit.ExplicitMode=None`. Unfiltered All/Unit runs must execute tests in every project. Integration and custom filters can leave individual projects empty, but the complete selection must execute at least one test. File persistence, transactions, extraction and native process/pipe checks belong in Integration; keep pure normalization, ranking and state checks in Unit where their fixtures do not require filesystem setup. Keep process-wide culture/environment/Trace changes isolated with restoration in `finally` or teardown and `NonParallelizable`; do not enable parallel execution globally. Sampling tests wait for publications; CLI debounce tests use an internal clock without changing the production 500 ms delay.

Persistence validation keeps archive headers, collection contents, metadata and numeric bounds in separate private checks. `InvestigationHistory.Valid` shares section validation between incident files and restart history; `IncidentRecording`, `UsageArchive` and `ResourceTrendArchive` validate before replacing saved files. The [November 21 CRAP remediation report](CRAP-REMEDIATION-2026-11-21.md) records the measured complexity, characterization tests and remaining work.

Service snapshot validation checks header/quality metadata, ordered windows/counters and bounded reading sets in that order. Private predicates preserve short-circuit behavior and the entry point's uniform wire error; process rows, endpoint parsing and raw five-part flow uniqueness retain their existing rules. The [snapshot validation batch](CRAP-REMEDIATION-2026-11-21.md#service-snapshot-validation-batch) records characterization, complexity and performance evidence, including existing acceptance rules left unchanged.

MCP hardware projection uses section-specific local functions while retaining two passes: project every section, then detect clipping against the original data. They share the identifier-policy capture. Response trimming retains its first-maximum tie order and halves only the selected collection; the response envelope applies aggregate truncation afterward. The [hardware projection batch](CRAP-REMEDIATION-2026-11-21.md#mcp-hardware-projection-batch) records privacy, text/list bounds, metadata and evaluation-order tests, plus synchronous projection and full response measurements.

MCP performance aggregation keeps window advancement and validity checks in `Add`, projects the sixteen named/unit-bearing readings through `ReadValues`, then accumulates total and bucket overlap. The reader's inlining hint preserves the measured allocation behavior of its short-lived tuple array; rerun aggregation measurements before changing it. The [metric projection batch](CRAP-REMEDIATION-2026-11-21.md#performance-aggregate-metric-projection-batch) records state/exception contracts and an existing weighted-overflow edge case left unchanged.

MCP performance sampling validates the request before slot acquisition/cancellation, then pins its initial process lifetime. A local observer shares that identity and lazily retains one matching predicate per request. Collection errors and target changes are recorded before lifetime exit; gap frames do not end the lifetime. The original slot/lease scopes and duration-plus-two-second deadline remain in the orchestrator. The [sampling lifecycle batch](CRAP-REMEDIATION-2026-11-21.md#sampling-lifecycle-batch) records deterministic frame/deadline tests and controlled asynchronous request measurements.

MCP per-process traffic requests validate sort/limit/identity before cancellation or acquisition. A static local predicate owns those checks. The existing lease contains traffic enablement and current-frame access; token/domain selection precedes quality/status handling, and cached Windows-lifetime names precede full-frame fallback. Unavailable observations preserve session totals while suppressing rates. The [traffic-query batch](CRAP-REMEDIATION-2026-11-21.md#mcp-process-traffic-query-batch) records controlled subscription/publication, metadata/limit/quality and lease-release tests plus measurements with owner-validated session-GUID normalization.

MCP diagnostic responses enforce a 256 KiB limit on the complete serialized protocol message, including both structured content and its text copy. Oversized supported collections halve through one payload/count dispatch: history retains the newest suffix; others retain prefixes. Under-budget caller counts and flags remain unchanged. Counts rely on stable array lengths in sealed payload records. Callers must keep untrimmed envelope/metadata bounded: the serializer has an existing nonterminating fixed point if those fields alone exceed the limit. The [response-budget batch](CRAP-REMEDIATION-2026-11-21.md#response-wire-budget-batch) records exact-byte/type/exception tests, bounded hazard probes and full serialization measurements.

MCP recorded-performance-history requests check cancellation before validating options or identities. A static local function owns numeric limits and allowed sort names. The endpoint reads the retained snapshot once, selects an exclusive-start/inclusive-end UTC window, then ranks individual lifetimes or selects every row matching a pinned token/domain. Gap and stale historical points remain explicit. The [recorded-history batch](CRAP-REMEDIATION-2026-11-21.md#recorded-performance-history-batch) records controlled publication, window, ranking, retention and cancellation tests plus endpoint measurements.

MCP archive-history requests parse dates and identify the sort, then validate ordered date/options/path limits in a static local function before cancellation or the single archive read. Filtering uses public names only, retaining literal whitespace; result limits do not discard period totals or retained calendar bounds. The [archive-history batch](CRAP-REMEDIATION-2026-11-21.md#archive-history-batch) records exception/privacy/boundary characterization and controlled endpoint measurements.

MCP installer-registration tests use the existing injected process boundary and owned configuration/record files. Tests of the actual installer callback run in isolated child processes with child-only custom homes and an empty client search path, stopping before user configuration access. They must never invoke installed Codex/Claude clients or mutate user registration files. The [registration batch](CRAP-REMEDIATION-2026-11-21.md#installer-registration-batch) records preservation/error contracts and unchanged-production assembly evidence.

`ServiceTree.Capture` indexes current hosts, assigns owners, collects members and materializes groups in that order. The stages reuse the existing dictionaries and pooled lists. Cached owners remain tied to exact lifetimes; pending/stopped groups and unchanged service arrays retain their existing reference-reuse rules. Capture still requires serialized access and returns frames unaffected by later captures.

Windows service control keeps its public Task-returning entry point and uses real SCM/process operations with `TimeProvider.System`. An internal parameter-based boundary lets tests control native results and polling without global overrides or actual service actions. Stop/restart first validate the sampled service identity, then validate the opened process and requery the service before control. The caller owns the process through the stop wait and disposes it before a restart begins. Polling stays at 250 ms; the desired state is checked before the strict thirty-second timeout. Existing cancellation order is preserved, including a stop command that can precede observing cancellation. See the [characterization report](CRAP-REMEDIATION-2026-11-21.md#windows-service-control-batch) for contracts, default-adapter limits and the compiler-generated async metadata change.

Windows event message formatting uses an internal owned metadata boundary implemented by the existing native SafeHandle. The same private entry opens publisher metadata; the core retains the 1024-character initial buffer, 65536-character growth limit, exact success clamp/NUL trimming and existing retry/error/disposal rules. Tests use owned callback sequences; bounded read-only native probes validate missing publishers and an existing event without writing logs. Native probes remain separate from ordinary coverage and targeted simulated performance. See the [formatter batch](CRAP-REMEDIATION-2026-11-21.md#event-message-formatter-batch).

The Info dialog selects its on-demand hardware reader before the existing `Task.Run`. `HardwareInfoReader.For(owner)` returns the original cached `WindowsHardwareInfo.Read` by default; test-only owner overrides live in a lazily created weak table and restore the previous reader on disposal. Selection fixes the queued delegate, so later scope disposal cannot alter an already scheduled read. Native hardware collection remains outside the sampling loop. Controlled tests cover success/partial-data/errors/retry and closing, while native clipboard/full-device UI integration remains separate.
Disk hardware inventory keeps on-demand query/status/cancellation orchestration separate from one-row projection and strict unique relationship matching. Network table acquisition exposes its existing query callback/method/result internally for typed friend tests, with no algorithm or native-caller change. Network and sensor service startup share `ProtectedServiceIdentity.EnsureRunningAsync`. ## Code structure

Memory-pressure collection belongs to `WindowsResourceSampler`: one optional PDH query reads paging read operations/sec, three standby lists, modified pages and free/zero pages. The standby total requires all three readable lists. Paging reads are a rate; warm-up, reset/gap and invalid readings stay unavailable. Counter failure does not discard CPU, disk, network or GPU data. Compression store is the working set of an exact `MemCompression` or `Memory Compression` entry in the current uncompacted process sample, otherwise null; no process handle is opened for it. System cache remains the `GetPerformanceInfo` system-cache working set and is not standby.

The five nullable fields flow into memory details, `SnapshotText` capture reports and appended resource CSV columns: `paging_reads_per_second`, `standby_bytes`, `modified_bytes`, `free_bytes`, `compression_store_bytes`. Restart-history format 4 preserves them while keeping the format-3 fixture/reader; old snapshots load with unavailable values. Incident files retain compatibility because these are optional JSON resource members. Neither automatic-capture rules nor chart series gain a new memory-pressure metric.

Desktop process controls use `ProcessController` with `IProcessControlTarget` fakes and a native `WindowsProcessControlTarget` handle. Creation time, exit and critical status are checked on that handle before changing anything. Affinity is limited to one processor group and a nonempty subset of the system mask. Efficiency mode preserves unrelated throttling flags, explicitly controls execution-speed throttling, and changes priority separately; a failed priority change attempts to restore throttling and rereads both values. A mixed state is not reported as Off. Unsupported or denied reads remain unavailable.

`ProcessesView` separates captured action routing, end/dump eligibility and individual process-control operations. Suspension and affinity recheck current eligibility after their dialogs. The public constructor retains native adapters; internal instance-scoped adapters allow dispatcher characterization with fake control handles and no real process writes. They add one optional reference per view, with no dependency carrier allocated by the public constructor.

`SuspendedProcessTracker` keeps at most one outstanding Suspend per lifetime for the desktop session. Menu-time `WindowsProcessSuspension` snapshots distinguish observed thread suspension from WinMon's outstanding request; no thread-state query is added to sampling or per-frame rendering. A successful balancing Resume removes tracking even when another suspension remains. Confirmed exited/reused lifetimes are removed without resuming a different process; denied reads and failed Resume retain tracking. `MainWindow.OnClosing` resolves outstanding requests before update preference writes or session shutdown, with explicit Resume/Leave/Cancel choices. Failure or cancellation keeps the window open. Native process-control errors convert NTSTATUS to Windows error codes before using existing messages. Store verification covers this shutdown path; CLI and MCP controls remain unchanged.

Hardware inventory is an on-demand path independent of `MonitorSession`. `WindowsHardwareInventory` in MonCore.Windows owns typed Windows observations, native/WMI selection and disk joins. Desktop Info and CLI format the same snapshot into localized hardware sections; CLI `hardware --format json` and MCP `get_hardware_info` expose typed raw values. CLI watch appends F5 Hardware to the existing four enum values and normalizes older four-tab settings. Neither inventory contents nor identifier opt-in is persisted. A hardware refresh never runs in the one-second sampling/render loop.

MCP hardware uses a dedicated response envelope without sampled freshness. A single in-flight hardware worker retains ownership until native work exits even if its caller cancels; it does not consume performance-sampling slots. Hardware response serialization applies privacy projection, safe bounded strings and inventory-aware trimming within the complete 256 KiB result budget. See [the design](design/HARDWARE-CLI-MCP.md) and [implementation evidence](design/HARDWARE-IMPLEMENTATION.md).

The network client rechecks the monotonic one-second snapshot interval after every timer wait, rounding remaining delays up to whole milliseconds. The server keeps its strict request bounds and records snapshot/control rate rejections and request operation/stage/elapsed time. `ProcessNetworkSnapshot.IncompleteReasons` is an additive protocol-1 flags field (older peers default to None), validated by the client. The controller logs quality/reason/failure/generation changes and a summary at most once per minute while unchanged, including native/queue loss, late events, row/rate counts and window lag. Unavailable snapshots are logged before reconnecting. Seed/start ownership-probe failures alone do not imply missing traffic; unresolved observed packets do, including while ownership probes are cached as rejected. Ledger ambiguity suppresses only affected rate windows, retaining incomplete cumulative totals for the generation. See [network reliability diagnostics](design/NETWORK-RELIABILITY-DIAGNOSTICS.md).

`NetworkMonitoringController` owns one cancellable polling/recovery task. It polls healthy subscriptions once a second; an unavailable snapshot, pipe failure or request timeout releases the subscription and retries connection/subscription/health after five seconds. Failed startup restoration also starts this retry loop. Recovery never invokes setup or changes the logical session ID, so `ProcessNetworkSession` retains totals and suppresses rates across gaps. A protocol mismatch stops retries with Update required. Explicit repair, disable, removal and shutdown cancel and await the task before taking ownership of the connection. Tests use fake service connections; the UI benchmark disables the controller and does not measure recovery.

`ConnectionGraphData.Build` keeps connection-history filtering, scratch-map reuse, sample alignment and shared scale in one refresh coordinator. Its private owner/reading phase resolves wire and captured metadata before keeping the first reading per Windows lifetime; its rate phase applies current-lifetime membership, finite nonnegative rates and nullable executable-group totals. Both phases reuse the caller-owned dictionaries without extra capture passes.

`ConnectionDisplayRow.UpdateGroup` binds row state and coordinates network/accessibility, pin/icon updates and change notifications. Its private `UpdateLabels` formats the name, detail and protocol counts, preserving status and historical-path presentation before the remaining row updates.

The [optional network service](../src/WinMon.NetworkService/README.md) owns privileged ETW collection, process ownership and an authenticated local named pipe. `MonCore.Windows` contains its SCM-verifying client, protocol, setup-pipe native boundary and signed-package verifier; portable snapshots and quality flags live in MonCore. `MainWindow.NetworkMonitoring.cs` coordinates Settings and `NetworkMonitoringController` owns the live subscription. Its one-second IPC loop maintains the lease and latest snapshot independently of tab visibility; rates remain the service's delayed event-time rates. It does not calculate arrival-time rates. Accounted process traffic is retained with connection observations for Capture. The sampling options carry the latest immutable service snapshot and logical client-session ID to MonitorSession. Its UI-thread drawn owns ProcessNetworkSession accounting, preserves totals through CPU failures and service reconnects, and clears them only on a new logical session. Raw network QPC clocks are never rebased with resource history. Connections receives this live frame through its existing Update call.

`WinMon.NetworkSetup` is a standalone NativeAOT executable with a require-administrator manifest, sharing only source-generated setup wire/trust code with the adapter. Signed release packaging embeds it, the service archive and RSA-signed manifest into both WinMon.exe and WinMon.Cli.exe, so either app can explicitly provision the service. No bundle means no setup/UAC. Settings applies the toggle on Save, validates authorized subscription/health before saving enabled, and cancels failed setup without accepting the setting. Startup reconnects without provisioning; disabling unsubscribes without elevation. Explicit maintenance provisions the actual requesting pipe-server process SID, including when UAC uses another account, and installs only under `%ProgramFiles%\WinMon\NetworkMonitor`. Binaries, dependency files, inventory and SID policy remain administrator-protected. The helper serializes maintenance with an exclusive file in the protected parent, restores the prior tree/policy/service running state/DACL before commit on failure, and independently registers Windows Installed apps removal. Removal validates the owned inventory and refuses unrelated files. The installed helper schedules its own locked image/directory for deletion at reboot when necessary (exit 3010).

Explicit signed service repair accepts missing inventory-listed files only after validating the inventory identity, every remaining file/directory owner and ACL, and the absence of reparse points, unexpected files and unrelated directories. A missing or invalid inventory still fails closed. Repair keeps an incomplete old tree at a unique `%ProgramFiles%\WinMon\.NetworkMonitor-quarantine-*` path after health verification; failure before commit restores it through the existing rollback. Existing authorization policy is preserved when present; otherwise only the requesting SID is authorized. An available service executable or uninstall registration still supplies the downgrade guard. Removal accepts the same bounded incomplete inventory, deletes the owned service registration, then renames the tree to `.NetworkMonitor-removed-*` before deleting files. Failed file cleanup emits a warning trace and the remaining protected retired tree does not occupy the installation path. Retired/quarantined trees are retained rather than swept automatically. This is maintenance after administrator approval; background reconnect never provisions or repairs a service. See [Service installation recovery](design/NETWORK-INSTALLATION-RECOVERY.md).

Pipe snapshot preparation keeps the one-second request budget, collector read, generation reset, checked per-subscription sequence and payload fitting together in `NetworkPipeServer.PrepareSnapshot`. `ServeAsync` owns dispatch, diagnostic stages, transport writes and lease cleanup. Wire characterization covers generation changes, collector immutability, bounded payloads and callback/disposal failures.

The network collector returns to cancellation and its reconciliation deadline after each 4,096-event batch. A failed creation probe or detected PID reuse closes the previous lifetime at the earlier of the inferred end and its last native verification, marking excluded intervals as `AmbiguousLifetime`. Explicit process-stop events retain their observed boundary. Regression cases cover account-filtered counters/endpoints across uncertain exits, verified successor traffic, legitimate delayed packets, maintenance with a nonempty queue and cancellation between batches. See [collector audit corrections](design/NETWORK-COLLECTOR-CORRECTIONS.md).

Rules for new code:

- **`MonCore` is portable.** It references no WPF, Windows Forms, Avalonia, System.Management or native imports. `AssemblyBoundaryTests` checks assembly references and imports, and `MonitoringLayerTests` checks compiled type use.
- **The Windows adapter depends on MonCore.** WinMon references both projects. `MonCore.Tests` references only MonCore; `MonCore.Windows.Tests` references the adapter.
- **Sampling lives outside the window.** `MonitorSession` owns the capture loop, the queue and history. It reaches the UI thread through a `post` delegate the window supplies.
- **Capabilities and observations are separate.** `IFrameSource.Capabilities` says which system and process metrics and actions an implementation supports. Nullable readings still report per-sample unavailability, and process actions recheck the lifetime and Windows permission at execution.
- **A view is a UserControl updated through one `Update(...)` call.** It raises events when the user changes something; the window keeps persisted settings in `MonitorPreferences` and passes them back in.
- **XAML for layout and window chrome; code-built elements only for rows updated every tick.**
- **Diagnostics and the benchmark use internal members, never reflection on WinMon's private names.** When one needs more, add a named member to `MainWindow.Internal.cs` or the view.
- **Structural changes must not regress performance.** Measure before and after as described under [Performance](#performance).

## Measurement semantics

### Resources

- **Logical processors** adds a CPU-only grid to the existing chart dropdown. Each processor's utilization is `(kernel + user − idle) / (kernel + user)` over successive Windows [SystemProcessorPerformanceInformation](https://learn.microsoft.com/windows/win32/api/winternl/nf-winternl-ntquerysysteminformation#parameters) readings, on its own 0–100% scale. Kernel includes idle. The machine and process percentages keep their existing total-capacity denominator. A missing or invalid processor reading breaks that processor's trace; an optional per-processor query failure leaves total/process CPU sampling intact. Grid cells share the selected chart range and historical interval. Processor count changes require a fresh baseline. Short cells use labeled sparklines, with values in tooltips and UI Automation; larger cells also display a percentage and grid guides.
- CPU, memory, disk and GPU traces use a fixed 0–100% scale; network throughput uses its own visible-peak scale.
- The chart toolbar keeps Auto immediately after the centered Live/Capture switch, without shifting that switch; the 150-DIP chart type selector stays on the left and time ranges stay on the right. Its width accommodates Logical processors; longer translations remain available in the tooltip. The former "2m peak" legend and tooltip are absent. The gauge setting explains the dark peak mark and its configurable window.
- Resource-detail values and labels wrap rather than trim. CPU ACPI zones use a full-width row below their heading; CPU sensor-source metadata is omitted. Temperature peak times use the current culture's short local time format and the CPU temperature peak label states its fixed ten-minute window. CPU usage peak headings retain the configured gauge window. A CPU performance-limit reading of 100% displays the localized no-limit status.

- Resource gauges in Full and Compact views are drawn by `MetricGauge` in the `GaugeStyle` chosen in Settings (default Bowl). Each gauge shows the live level and a dark peak line. GaugePeakWindowSeconds selects 60, 120 (default), 300 or 600 elapsed seconds, independently of chart range. Peaks retain the newest maximum sample, skip gaps and invalid readings, match configured disk volumes and keep network readings on the latest adapter. Only retained samples contribute; a shortened history can cover less than the requested window. Full-view tiles use symmetric horizontal margins so each bowl and value share the center of their column. Arc styles put a decorative peak-marker icon and value beside CPU, memory, disk and GPU names at every width; the accessibility name and tooltip retain the Peak label. Peak labels always use RAM used, disk throughput or dedicated GPU memory from the utilization-peak sample when available, otherwise a percentage. It does not change live readings. The shared resource tooltip includes the peak, its local timestamp and age relative to the latest sample, with monotonic elapsed time where available; it is available on the tile, corner and keyboard focus in both views. MetricDetails formats that section only while open. `MetricReadout` accounts for each tile's outer margin to place the corner label 12 DIPs from its right edge. The network gauge displays received bytes per second on its own peak-window auto scale, which matches the chart when both ranges agree; arc styles print the download peak (`RateText.Short`, such as "8MB/s") with the peak icon; the tooltip prints the full rate and top of the automatic scale. Percentages use 0–100. An unavailable current reading hides its gauge and corner label. Every style fits `MetricReadout.LayoutHeight`; see [Gauge styles](design/GAUGE-STYLES.md) for the layouts.
- **CPU clock** (`ResourceSample.CpuClockMhz`, the gauge detail, CPU details, CLI and the `cpu_clock_mhz` CSV column) is the effective clock: the highest `MaxMhz` from `CallNtPowerInformation(ProcessorInformation)` × `\Processor Information(_Total)\% Processor Performance` / 100. The highest rated clock is Windows' base speed, so hybrid processors match Task Manager's Speed. `CurrentMhz` from the same call is not used, because some processors (Ryzen 9000) report only the rated clock there through idle and boost. The counter is a rate read with `PDH_FMT_NOCAP100` from the memory-pressure query, so the sampler opens no extra query. Values above the rated clock are kept, never clamped. The first sample, the first after a gap or query failure, and any failed, non-positive or non-finite reading are unavailable; the rated clock never stands in. Info's maximum clock is the reported specification. See [the design note](design/EFFECTIVE-CPU-CLOCK.md).
- **System handles** (`ResourceSample.HandleCount`, shown in CPU details) is the sum of every process's handle count from the CPU sampler's full `SystemProcessInformation` snapshot, matching Task Manager. It covers the first sample after a gap and processes started within the last second, which have no Processes-tab row yet. `GetPerformanceInfo` adds the System process's handles a second time, so its total is used only when the snapshot reaches its process cap or a process lacks a count. Process and thread totals still come from `GetPerformanceInfo`.
- **Memory** is used over total OS-visible physical RAM, with GiB readouts.
- **Disk** is active time (`100 − % Idle Time`) on each configured volume, with read/write throughput in decimal MB/s. It is not space used. Drive letters identify logical volumes, which may share a physical disk, so disk percentages are never added together.
- **Network** measures one connected Ethernet or Wi-Fi adapter. Automatic selection prefers one with a gateway, then the fastest, and keeps that choice while it stays connected. Network settings can instead hold a specific adapter ID; if it is disconnected or missing, readings stay unavailable rather than switching adapters. Adapters are re-enumerated after a Windows network-change event or every 30 seconds; counters are read every second. Changing the selected adapter resets rate and total baselines. Traffic readouts use adaptive decimal KB/s, MB/s or GB/s, while adapter link speeds in resource details and hardware inventory retain Mbps/Gbps. The gauge leads with receive and shows send below; utilization uses the busier direction over the reported link speed. Graph scales and samples remain bit-based internally. Automatic capture thresholds display MB/s and convert to/from the existing stored Mbps values, preserving saved rule behavior. Connections totals and owner details explain the five-second averaging window ending normally three seconds behind the current time in their tooltip and accessible text. This is link utilization, not Internet bandwidth.
- **GPU** reports the busiest physical engine across adapters by default, or within the selected GPU, from the Windows GPU Engine performance counters, without vendor libraries. Process contributions are summed within each engine before the busiest is chosen; independent engines and GPUs are never added. Optional D3DKMT performance readings supply temperature, fan RPM and power per physical adapter; pair by LUID plus physical index rather than averaging. Unsupported values stay null. The CPU performance-limit counter reports a generic limit, not a thermal diagnosis. ACPI thermal-zone values are labelled system zones and stay in details, outside the CPU gauge. Celsius is canonical; the display unit is a preference. See [temperature monitoring](design/TEMPERATURE.md) for validation and native acceptance limits.
- Interface or speed changes, counter resets, startup and long collection gaps need fresh rate baselines. The received and sent totals restart only when the adapter changes or its counters go backwards. Unavailable metrics show a dash and break the trace. A CPU provider failure does not stop the other resources. A capture that fails, or a sampler that cannot start, shows readings unavailable and is retried each second.
- Machines with more than one active processor group are unsupported and show unavailable CPU readings rather than partial machine totals; an update there proves healthy from the other resources.

Automatic capture report writes are tracked on the UI thread. Normal close and in-app update restart wait for them, like CSV exports and process dumps, before closing the window or committing the update. The capture smoke includes a delayed-write shutdown check in `captures.json`. A stalled report destination can delay exit; forced termination and Windows session shutdown do not provide this asynchronous wait.

`MainWindow.OnClosing` cancels the initial Closing event while it completes shutdown. Its final `Close` is queued through the dispatcher so completed awaits cannot close the window recursively within the original event. `NormalShutdownCharacterizationTests` covers completed work and pending writes.

Network-triggered reports append executable leaders from the exact peak's retained ConnectionCapture.Network, rather than the latest live frame. Process lifetime identity governs metadata; executable instances share a rate row, and unavailable member rates keep that direction unavailable. Reports preserve quality and delayed-window notes and distinguish the selected-adapter trigger from all-adapter app traffic. The total-I/O fallback remains explicitly disclaimed.

Invalid JSON settings whose backup fails remain protected: subsequent saves retry the backup and fail without replacing the original until it succeeds.

### Processes

The desktop opts into MonitorSession's bounded UsageHistory, recorded from uncompacted samples independently of ranking retention. It stores interval CPU/I/O/GPU deltas and lifetime metadata, with the configured resource-history duration and a separate 500,000-observation budget. Oversized samples become unavailable coverage; restored compacted samples never feed it. Query aggregates whole intervals, detects gaps and caches the selected endpoint/range until eviction. Its original interval observations are optionally persisted across normal restart and always included in update-restart history, without feeding compacted samples back into the ledger. The CLI also opts into period retention for historical Usage. The benchmark includes usage-ledger-and-history-add alongside the unchanged usage-ledger-add case.

Capture mode adds one shared coverage line above the activity body. It separates actual retained span from exact selected-observation availability, exposes memory limits and explains independent budgets and restart persistence. Its tooltip computes all source bounds only when opened; normal refreshes do not aggregate a hidden Usage period or copy connection history for this line. Live mode hides it. A retained span does not imply gap-free data.

Process More/row menus route to Connections and Usage through captured ProcessDetailsSnapshot targets, including an exact SampleKey in Capture mode. Stale moments and reused process identities cannot silently retarget a command. Connections requires observed endpoints and matches executable paths or PID/start tokens; Usage uses its existing executable policy. Navigation clears restrictive filters and changes Top to All only if the target is otherwise outside the ranked rows (the changed view preference is saved normally). Live Usage eligibility uses the ledger's key lookup without materializing its app snapshot. A cached period survives evictions outside its requested interval; evicting an included interval still recomputes partial totals.

Portable lifetime, executable equality and CPU availability contracts are described in [Portable process identity](design/PORTABLE-PROCESS-IDENTITY.md). Windows defaults and history format 1 remain unchanged; portable consumers use `ObservedCpuPercent` and explicitly select their identity policy.

Services row refresh ranks and filters groups before building expanded children through the local `AddExpandedRows` function. `PublishRows` reconciles the observable collection, spare header cache and action selection; `RefreshStatus` then updates notices and pin counts. These phases stay inside the refresh's existing try/finally so observer exceptions still restore selection handling and update buttons.

- Process CPU is a share of total machine CPU capacity, not per core or lifetime. CPU, GPU and I/O columns use a five-second window.
- The list ranks by CPU, GPU, Memory, I/O, Threads or Handles (`ProcessSort`). Memory, Threads and Handles rank the latest observation of processes in the newest sample.
- **Memory** is the resident working set, including shared pages. **Grouped** rows instead sum the private bytes of current members, since working sets share pages.
- Processes and Services keep units in numeric cells: CPU/GPU percentages, memory in adaptive binary B/KiB/MiB/GiB/TiB and read/write I/O rates in adaptive decimal B/KB/MB/GB/TB per second. Scaled memory and I/O values use one decimal place; bytes use whole numbers. Their headers use metric names only; Services labels private-memory totals as Memory. Usage already keeps Share's percent sign and adaptive decimal byte units in its cells.
- **GPU** per process is its busiest engine per interval, averaged over readable intervals. A missing counter or unverified process lifetime shows a dash. Per-process GPU is not additive, so a group shows its busiest member and the Other processes GPU cell is a dash.
- **I/O** is interval read/write MB/s and includes file, network and device operations; it is not disk-only.
- Grouping identifies executables by full path, falling back to the process name when the path cannot be read.
- Sparklines plot one-second values of the ranking metric over the last two minutes, on one shared scale across rows (zero to the busiest listed row's visible peak with headroom).
- Listed rows plus Other processes need not sum to the machine total. The Process column heading reports the unattributed remainder, and very short-lived processes can exit between polls.

### Collection and history

- Restart-history format 4 includes nullable memory-pressure readings; format 3 added per-logical-processor readings. Formats 1–3 still load, with fields absent from their encoding unavailable; older builds cannot restore format-4 history. Normal restarts and update restarts use the same versioned sample encoding.
- MonCore's `MonitorSession` owns history, latest samples, usage and service frames on the thread selected by the caller's `post` delegate. The synchronous collection loop runs on one dedicated background thread (`LongRunning` on the default task scheduler), with `AboveNormal` priority on Windows; if setting priority fails it logs a warning and continues. Stopwatch deadlines and a cancellable wait keep ticks independent of thread-pool timers and continuations, account for capture time and skip missed deadlines without accumulating catch-up work. It enqueues captures in order and never waits for the UI to drain them. Call session state operations on the dispatch thread; cancellation wakes the wait, ends collection after an in-flight native capture returns, and `Close()` discards later drains. CPU saturation, blocked native calls and suspend can still delay observations; chart and sampler gap thresholds remain unchanged.
- MCP `sample_performance` requires a fresh initial frame, then aggregates queued observations by their recorded times within the requested window. A delayed consumer does not invalidate retained intervals or postpone a recorded process disappearance. Gap, interval and metric validity checks still determine coverage, and the request stays pinned to the initial process lifetime.
- `ProcessUsage.CreationTicks` remains Windows FILETIME in the current Windows collector and saved-history format. A portable lifetime/start-time model is required before a macOS collector writes samples or persistence. Group keys currently compare executable paths without case, preserving WinMon behavior.
- CPU percentages are shares of total machine capacity; I/O rates use bytes per second, GPU is the busiest engine, and unavailable readings stay null. `WorkingSetBytes` is resident memory and `PrivateBytes` is private committed memory; a macOS footprint needs its own measurement contract.
- All processes come from one `NtQuerySystemInformation(SystemProcessInformation)` call, without opening process handles, so access-restricted processes are measured too. The buffer is pinned and reused, and collection stops at 20,000 processes, counting any beyond.
- Collection is sequential within one pass, not an atomic snapshot across Windows APIs.
- `ProcessRetention.Compact` keeps, in each retained sample, the processes with CPU, I/O or GPU readings, processes that have shown an app window, pinned processes, and the 50 largest working sets, thread counts and handle counts (ties at the cut-off are all kept). Dropped entries are counted in `CompactedProcesses`, and averages treat them as zero.
- `MonitorHistory` holds up to a 500,000-process-entry budget; the UI reports when that shortens the retention window. Service history follows History.Capacity under its own 120,000-observation bound and reports memory-limited retention. Service row charts keep their existing two-minute window.
- History is in memory by default. In-app updates save it for the new version to restore; see [the design note](design/UPDATE-RESTART-HISTORY.md). The optional normal-restart snapshot saves compacted samples beside settings, then consumes the file on startup before sampling. It rebases historical monotonic timestamps onto the current process clock and shifts live samples by the same offset when needed after a reboot. Separate optional checksummed investigation chunks carry service groups, endpoint/traffic captures and uncompacted Usage intervals aligned to exact sample keys. Normal restarts rebase their keys with resource samples; restored traffic never seeds live counters. The test-only override is execution-context scoped and restores the previous provider once; its AsyncLocal slot is created only when a test supplies an override. This keeps the existing four-field worker capture without adding a MainWindow reference. Controlled tests exercise success/errors/cancellation and exact elevation requests without service control or process launch; actual non-null helper wait/exit/disposal and UAC integration remain open. See [service-action verification](CRAP-REMEDIATION-2026-11-21.md#service-action-scoped-io-characterization-revised-limit-met-november-24) and the performance history for measured default forwarding.

`MainWindow.OnExport` still captures data on the UI thread, starts a background write, registers it in ExportWrites, awaits it and reports the result. Internal `CsvExportOperations` supplies the real chooser, native Save dialog and CsvExport.Write by default; its test-only provider is scoped through a lazily created AsyncLocal slot. This preserves worker captures without a window reference. The chooser remains before the file-error try; save/write failures stay inside it. Writes are not canceled by the window lifetime; shutdown joins pending writes and rechecks for newer ones, suppressing their failures. Completed tasks remain registered until the success notice closes. Controlled tests cover these contracts without native Save/file writes; actual Save integration remains open. See [export I/O verification](CRAP-REMEDIATION-2026-11-21.md#export-io-producer-contracts-characterized-complexity-still-above50-november-24) and the performance history.

`MainWindow.RefreshConnections` selects the live or retained sources and computes the traffic window. `UpdateConnectionEndpointCounts` updates the TCP/UDP header before that computation; `UpdateConnectionTrafficStatus` formats volume, warnings and accessible details afterward. The connection list updates last, unless the activity panel is collapsed. The diagnostic-live source decision is shared only before the first UI update; later selection reads retain their existing position relative to property notifications.

### Profile the whole app

`--profile-output <dir> [seconds]` runs the real window and sampler in isolation, waits 20 seconds, then measures for the given duration (default 60, 10–3600). It writes `profile.json` with CPU per second, working set, private bytes, managed heap, allocation rate, GC counts and retained process entries, reading memory for this process only. Run both builds side by side and swap launch order, because the first-launched instance tends to use more UI-thread time. Run at least 150 seconds when service history matters, so it reaches its two-minute steady state.

### Where the time goes

As of October 2026 (see the [history](PERFORMANCE-HISTORY.md#chart-drawing-and-refresh-october-22-2026)):

- The process snapshot dominates sampling, and its cost follows the machine's thread count, because the query returns every thread. It is the OS floor for 1 Hz sampling.
- On the UI thread, WPF text formatting and layout of values that actually changed is about half of a live frame; WinMon's own refresh and chart drawing are the rest.
- Whole-app CPU barely moves with UI-thread savings. Allocation and private bytes are the more sensitive measures.

### Decisions in force

| Decision | Why |
| --- | --- |
| Gen0 budget capped at 6 MiB | Private bytes 86 → 52 MiB in a 60 s profile, for cheap extra gen0 collections |
| Single-file compression off | About 130 MiB less working set and faster startup |
| Default tiered PGO kept | Turning it off cuts launch CPU but only breaks even after about an hour |
| No ReadyToRun | Most tier-1 work is already-precompiled WPF code; +20 MB for little gain |
| Retain only active, app, pinned and largest processes | About 87% fewer retained process entries at 10 minutes |

### Services and Connections CSV

CSV export snapshots Services.Frames and Connections.Captures on the UI thread before writing on a worker. Chart-range filtering uses the latest retained resource monotonic moment as its end, matching resource/process exports; wall-clock-only fixtures fall back to their timestamps. Services uses its separate 120-second/observation-budget history; Connections uses its bounded in-memory history. Neither falls back to live data. Services writes one row per service with raw numeric SCM state and host-only metrics (shared host metrics repeat; workers are excluded). Connections writes individual endpoint rows with strict PID/creation-token owner matching, TCP state and per-address-family availability, without traffic counters. The separate NetworkTraffic kind exports each retained process lifetime once per sample (including owners without endpoints), cumulative session bytes, delayed rates and numeric quality flags. Metadata matches the full lifetime identity; unavailable rates remain blank. Empty/unavailable frames produce timestamp/availability rows. UI filters and grouping do not alter exports.

Settings numeric capture fields and activity ranking/filter controls expose localized tooltips and automation help text. Connections ranking retains its unavailable-monitoring explanation.

### Chart resource legend

Full-view MetricReadout tiles use plain resource names. Their existing Toggle controls are hosted by ContentControls in the wrapping ChartLegend inside ChartBody, with the same saved series mask and localized labels. ChartLegend is centered in a compact themed border above the plot, using 12-DIP checkbox text and tighter spacing. The graph and SnapshotLayer share the next grid row and coordinates. The chart minimum height includes the measured legend host height. Logical processors hides the legend; chart collapse hides the whole body and recovers keyboard focus. Gauge tiles retain keyboard access to detail tooltips. Chart smoke includes ownership, chart-type visibility, narrow German two-disk layout and collapse/expand checks.

The cog button beside the chart selector uses ActivityPanelButton for native expand/collapse automation. MainWindow.ActivityPanel keeps the persisted control-visibility flag, tooltip and minimum height together. ### Per-chart preferences

ResourceChartPreferences stores the raw six-resource mask, range, control visibility and focus index for each chart type. MonitorPreferences keeps the legacy top-level fields as the active chart state, snapshots them before switching and restores the selected type. PreferenceStore validation seeds missing entries from legacy selections and range, normalizes persisted entries and snapshots the active configuration before save. The raw mask retains the second-disk selection without a configured second drive. Longer saved ranges remain stored when retention is reduced; EffectiveChartRange uses two minutes until that choice is available again. SettingsWindow defers chart reset until Save and merges ordinary settings without overwriting current chart choices. See docs/design/CHART-PREFERENCES.md for requirements and validation limits.

Preference validation shares count, enum and column-range policies across fields while keeping each field's fallback. Service name sorting remains available only for the raw saved all-services count; normalizing an unsupported count does not enable it. The initializer retains its existing field evaluation order and snapshots chart configuration after validation.
