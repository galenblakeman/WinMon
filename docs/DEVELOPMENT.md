# WinMon developer guide

ReSharper uses the shared `WinMon.sln.DotSettings` syntax policy and dictionary. Keep correctness inspections enabled and explain intentional exceptions beside the source. The [inspection review](INSPECTION-REVIEW.md) records the disposition of the November 8, 2026 report.

`SelectedActivityTab` persists the last activity tab (Processes=0, Services=1, Usage=2, Connections=3). Missing or invalid values select Processes. Startup restores the tab after loading view preferences, suppressing the usual tab-selection expansion so the saved collapsed state is preserved. Tab changes use the existing exit-save path.

Services persists `ServiceSortColumn` (CPU=0, memory=1, I/O=2, name=3), `ServiceStatusFilter` (all=0, running=1, stopped=2) and `ServiceIncludeWorkers`. Missing keys retain CPU/all/workers enabled. Name sort is valid only with Top set to All (0). Startup restores these controls after Top, suppressing change events while restoring; user filter changes update the immutable preferences saved through the normal exit path.

## Requirements

- Windows x64.
- The portable `MonCore` project and `MonCore.Tests` target plain `net10.0`; they can also build and run on macOS with the .NET 10 SDK. That macOS run is a separate verification step.
- The .NET SDK pinned in [global.json](../global.json) (10.0.402, latest-patch roll-forward).
- An interactive desktop session for the smoke modes and the benchmark, which open real windows.

## Build and test

```powershell
dotnet build WinMon.sln -c Release -m:1 -p:UseSharedCompilation=false
dotnet test tests/WinMon.Tests/WinMon.Tests.csproj -c Release -m:1 -p:UseSharedCompilation=false
dotnet test tests/MonCore.Tests/MonCore.Tests.csproj -c Release -m:1 -p:UseSharedCompilation=false
dotnet test tests/MonCore.Windows.Tests/MonCore.Windows.Tests.csproj -c Release -m:1 -p:UseSharedCompilation=false

dotnet test tests/WinMon.NetworkService.Tests/WinMon.NetworkService.Tests.csproj -c Release -m:1 -p:UseSharedCompilation=false
dotnet test tests/WinMon.NetworkSetup.Tests/WinMon.NetworkSetup.Tests.csproj -c Release -m:1 -p:UseSharedCompilation=false
dotnet test tests/WinMon.NetworkProbe.Tests/WinMon.NetworkProbe.Tests.csproj -c Release -m:1 -p:UseSharedCompilation=false
dotnet publish src/WinMon/WinMon.csproj -c Release -m:1 -p:UseSharedCompilation=false
dotnet pack src/MonCore/MonCore.csproj -c Release -m:1 -p:UseSharedCompilation=false -o artifacts/local-feed
```

`tools/Verify.ps1` builds all projects in the solution, builds the benchmark, runs all six test projects and any [smoke modes](#smoke-modes) in one step; see [Verify a change](#verify-a-change).

The [ETW network prototype](../tools/WinMon.NetworkProbe/README.md) and its `WinMon.NetworkProbe.Tests` project build and run as part of `Verify.ps1`. Its native collection experiment is `[Explicit]`, so it remains opt-in and requires an elevated approved Windows test environment; it installs no service and is not part of the shipping app. `Verify.ps1` passes `NUnit.ExplicitMode=None` to the NUnit3TestAdapter 5.2.0, so even a narrow filter cannot run an explicit fixture. To opt in manually, run `dotnet test` directly with a positive filter for the approved fixture; see [NUnit's Explicit documentation](https://docs.nunit.org/articles/nunit/writing-tests/attributes/explicit.html).

- Every build, test and release script passes `-m:1 -p:UseSharedCompilation=false`; keep them on manual commands too.
- `TreatWarningsAsErrors` is on for the app and both libraries.
- `-p:StoreBuild=true` builds the Microsoft Store variant, which defines `WINMON_STORE`, drops the GitHub updater, and targets `net10.0-windows10.0.17763.0` so sign-in startup can use the package's `StartupTask`. The test and benchmark projects switch TFM with it. `StoreBuildTests` covers what differs, so run the tests in both variants after touching update or Settings code.
- Inside a sandbox the VSTest host can fail to connect. The same command passes outside it.
- Run the native Services smoke outside a restricted sandbox. SCM enumeration returned Win32 error 5 (Access denied) inside the sandbox on the development machine, leaving every service frame unavailable; the same collector and smoke passed outside it.
- When the NuGet audit endpoint is unreachable, add `-p:NuGetAudit=false` to that command only, and note that the run skipped the vulnerability audit.

`dotnet build` output is at `src/WinMon/bin/Release/net10.0-windows/win-x64/WinMon.exe`, and `dotnet publish` writes the single-file distribution to `…/win-x64/publish/WinMon.exe`. Release builds are self-contained, optimized and embed their debug symbols. Two settings in `WinMon.csproj` are measured choices; the [performance history](PERFORMANCE-HISTORY.md#allocation-gc-and-compression-october-20-2026) has the numbers:

- **Single-file compression is off.** Compressed assemblies are inflated into private memory instead of mapped from the file, which roughly doubled the working set and slowed startup, in exchange for an executable about 90 MB smaller.
- **The GC gen0 budget is capped at 6 MiB** (`System.GC.Gen0MaxBudget`), in every configuration. Workstation GC sizes gen0 from the L3 cache, and at WinMon's allocation rate the app committed the whole budget between rare collections. The setting is undocumented, so confirm with `GC.GetConfigurationVariables()` that it still applies after a runtime upgrade.

## Verify a change

```powershell
./tools/Verify.ps1                                # build (app, tests, benchmark) and run the tests
./tools/Verify.ps1 -TestScope Unit                 # tests without Integration or Elevated categories
./tools/Verify.ps1 -TestScope Integration          # only Integration-category tests
./tools/Verify.ps1 -Smoke feature, services       # also run those smoke modes
./tools/Verify.ps1 -Smoke all -Store              # every smoke mode, against the Store variant
```

The script builds into `artifacts/verify/build` (or `build-store`), so it leaves your normal `bin` folders alone. Each run has a unique desktop/store timestamp folder under `artifacts/verify/`; it contains one TRX result per test project. Each test result line reports the TRX passed, failed and not-executed totals, and a missing TRX fails verification. `-TestFilter` accepts a normal `dotnet test --filter` expression and combines it with `-TestScope`; all scopes force `NUnit.ExplicitMode=None`. The script prints a pass or fail line per step, shows the start of `failure.txt` for any failed mode, and exits non-zero if anything failed. Open the PNGs it lists to check the renders; a passing exit code checks behaviour, not appearance. `-SkipTests` goes straight to the smoke modes after building.

Updater regressions live in `UpdateTests`, `UpdateDownloadTests`, `UpdateHelperTests` and `StoreBuildTests`. The lifecycle fixtures use signed manifests and real temporary-file transactions with controlled HTTP/process boundaries; they never execute fixture installers or replace the running app. Run both Desktop and Store verification after changes. See [update lifecycle coverage](design/UPDATE-LIFECYCLE-TESTS.md) for the boundary and native acceptance limits.

### Diagnostic log collection

For a focused logger comparison, `--live-only` runs the existing live-frame workload (400 warm-up frames and seven batches of 60) and writes its JSON/PNG without the unrelated UI/history scenarios. Alternate four runs each with and without `--without-logging`. The benchmark uses a `Logs` directory beside its JSON output, fails if the writer cannot be created, and records `LoggingEnabled` for checking the comparison.

Elevated app/helper launches use administrator/System-protected `%PROGRAMDATA%\WinMon\Logs\Elevated\<SID>` logs instead of ordinary user-writable folders. The same 10 MiB active app-set budget applies. The benchmark initializes app logging by default; pass `--without-logging` after its output and screenshot paths to isolate the logger's UI cost without changing other code.

`MonCore.Windows/Diagnostics/DiagnosticLog` installs a bounded rolling `TraceListener` in each app/service process. App startup attaches it before preferences are read; the service attaches before its SCM startup callback. Network setup provisions protected ProgramData folders and per-account permissions. The app falls back to LocalAppData if its ProgramData folder is unavailable, including Store/portable launches. See [the logging design](design/DIAGNOSTIC-LOGGING.md) for paths, limits, permissions and failure behavior.

Use constant, code-owned Trace templates. String values and exception messages are omitted; pass exception objects to preserve types, HRESULT/native codes and method stacks. Never interpolate process names, paths, account names, endpoints or secrets into the template itself. Repeated warning/error templates are summarized once per minute and during bounded shutdown. The writer performs a final summary and drain before releasing its file lease, including when it observes shutdown before the caller queues the summaries. A 512-entry queue, five 2 MiB files per set and bounded shutdown keep logging off the sampling/rendering disk path. `DiagnosticLogTests`, `LogDirectoriesTests` and the Info tests cover the writer, fallback, permissions and action layout; the `feature` smoke renders Info/About.

### Smoke modes

The shipped executable checks itself against live samples. Each mode opens an isolated window that bypasses the user's preferences, startup registration and single-instance lock, writes its evidence to the output directory, and exits 0 on success. On failure it exits 1 and writes the exception to `failure.txt`. Because `WinMon.exe` is a WinExe, PowerShell returns before it exits; wait for it to get the exit code:

```powershell
$run = Start-Process src/WinMon/bin/Release/net10.0-windows/win-x64/WinMon.exe -ArgumentList '--feature-smoke-output', "$PWD/artifacts/feature-smoke" -Wait -PassThru
$run.ExitCode
```

Limits:

- General UI diagnostics time out after 90 seconds; the remaining non-profile modes use 60 seconds. The full smoke includes a 15-second quiet observation as well as feature and fixture renders, so its budget allows slower CI desktops to finish. Verification and installer validation wait at most 120 seconds for smoke completion.
- Use a new output directory for each run.
- Renders at several scales are layout evidence. They do not prove real DPI changes, mixed-DPI monitor moves, keyboard automation, tray interaction or startup at sign-in, which remain manual checks. Smoke never ends a process or changes a service.
- Some renders use labelled illustrative data, such as `design-compact*.png`; they compare against the design reference and are not measurements.

Process Properties and Copy details share `ProcessDetailsSnapshot.Format()`. File and product versions come from the existing per-path `ProcessAppNameProvider` cache on the sampling thread; opening details performs no file I/O. Restart-history formats 2 and 3 preserve both strings; format 1 loads with empty versions. The current format 3 also preserves logical-processor readings. Older WinMon builds cannot restore format-3 history.

## Code structure

The network client rechecks the monotonic one-second snapshot interval after every timer wait, rounding remaining delays up to whole milliseconds. The server keeps its strict request bounds and records snapshot/control rate rejections and request operation/stage/elapsed time. `ProcessNetworkSnapshot.IncompleteReasons` is an additive protocol-1 flags field (older peers default to None), validated by the client. The controller logs quality/reason/failure/generation changes and a summary at most once per minute while unchanged, including native/queue loss, late events, row/rate counts and window lag. Unavailable snapshots are logged before reconnecting. Seed/start ownership-probe failures alone do not imply missing traffic; unresolved observed packets do, including while ownership probes are cached as rejected. Ledger ambiguity suppresses only affected rate windows, retaining incomplete cumulative totals for the generation. See [network reliability diagnostics](design/NETWORK-RELIABILITY-DIAGNOSTICS.md).

`NetworkMonitoringController` owns one cancellable polling/recovery task. It polls healthy subscriptions once a second; an unavailable snapshot, pipe failure or request timeout releases the subscription and retries connection/subscription/health after five seconds. Failed startup restoration also starts this retry loop. Recovery never invokes setup or changes the logical session ID, so `ProcessNetworkSession` retains totals and suppresses rates across gaps. A protocol mismatch stops retries with Update required. Explicit repair, disable, removal and shutdown cancel and await the task before taking ownership of the connection. Tests use fake service connections; the UI benchmark disables the controller and does not measure recovery.

The [optional network service](../src/WinMon.NetworkService/README.md) owns privileged ETW collection, process ownership and an authenticated local named pipe. `MonCore.Windows` contains its SCM-verifying client, protocol, setup-pipe native boundary and signed-package verifier; portable snapshots and quality flags live in MonCore. `MainWindow.NetworkMonitoring.cs` coordinates Settings and `NetworkMonitoringController` owns the live subscription. Its one-second IPC loop maintains the lease and latest snapshot independently of tab visibility; rates remain the service's delayed event-time rates. It does not calculate arrival-time rates. Accounted process traffic is retained with connection observations for Capture. The sampling options carry the latest immutable service snapshot and logical client-session ID to MonitorSession. Its UI-thread drawn owns ProcessNetworkSession accounting, preserves totals through CPU failures and service reconnects, and clears them only on a new logical session. Raw network QPC clocks are never rebased with resource history. Connections receives this live frame through its existing Update call.

`WinMon.NetworkSetup` is a standalone NativeAOT executable with a require-administrator manifest, sharing only source-generated setup wire/trust code with the adapter. Signed release packaging embeds it, the service archive and RSA-signed manifest into WinMon.exe, preserving single-executable portable updates. No bundle means no setup/UAC. Settings applies the toggle on Save, validates authorized subscription/health before saving enabled, and cancels failed setup without accepting the setting. Startup reconnects without provisioning; disabling unsubscribes without elevation. Explicit maintenance provisions the actual requesting pipe-server process SID, including when UAC uses another account, and installs only under `%ProgramFiles%\WinMon\NetworkMonitor`. Binaries, dependency files, inventory and SID policy remain administrator-protected. The helper serializes maintenance with an exclusive file in the protected parent, restores the prior tree/policy/service running state/DACL before commit on failure, and independently registers Windows Installed apps removal. Removal validates the owned inventory and refuses unrelated files. The installed helper schedules its own locked image/directory for deletion at reboot when necessary (exit 3010).

Service tests include native pipe ACL/authentication checks and deterministic delayed-event accounting; the bounded elevated collector experiment is explicit and excluded from normal verification. Setup tests cover payload paths, provisioned-state injection, permissions, inventory bounds, commit/cancellation and rollback orchestration. Store builds compile these components for compatibility but neither embed nor invoke the service setup. Real signed SCM installation, alternate-account UAC and reboot/rollback acceptance remain blocked as recorded in the [implementation checklist](design/PER-PROCESS-NETWORK-IMPLEMENTATION.md).

Connections supports live and captured observations. `WindowsConnections.Capture()` in MonCore.Windows reads owner-PID tables through [GetExtendedTcpTable](https://learn.microsoft.com/en-us/windows/win32/api/iphlpapi/nf-iphlpapi-getextendedtcptable) and [GetExtendedUdpTable](https://learn.microsoft.com/en-us/windows/win32/api/iphlpapi/nf-iphlpapi-getextendedudptable) for both IP families, with bounded allocation/retries and explicit family availability. A preliminary endpoint pass limits the process-lifetime probes to endpoint owners; matching creation tokens before and after the final tables prevent reused PIDs from acquiring process actions. Denied identity probes leave an unknown owner and generic icon without hiding the endpoint. A failed TCP or UDP table makes that address family's readings unavailable; the other family can still be shown with a partial-reading notice.

`WindowsFrameSource` reads endpoints on the existing sampling thread every tick, even when Connections is hidden. `MonitorSession` retains the observation, compact owner metadata and accounted process-network frame under the resource sample clock; raw network clocks are not rebased. `ConnectionHistory` uses exact sample lookup, chart time/count retention and a combined 100,000-entry budget for endpoints, owners and traffic readings. Missing, oversized, evicted and restored observations never fall back to live data. Connection history is not persisted across restarts. `MainWindow.Connections.cs` presents these observations, with unfiltered TCP/UDP counts and History received/sent byte totals beside the tabs; the selected period is in the tooltip; hidden activity rows are not redrawn.

`ConnectionsView.Update(...)` reconciles one row per case-insensitive executable path, with a lifetime-only fallback when path or owner metadata is unavailable. Endpoints appear only in Properties and copied details. Per-row pins reuse `ProcessPins`, grouped by executable when known and otherwise tied to the exact lifetime. `PinnedConnections` and `ConnectionPinnedOnly` persist independently of process pins; preference normalization validates identity domains and executable/lifetime scope. When an exact lifetime acquires executable metadata, its pin is promoted to the executable identity and duplicate pins are merged in original order. Pins keep insertion order above the ranked rows and do not consume Top; search and App only filter both sections. Missing pins retain display metadata, without stale endpoints or counts. A successful empty observation shows zero endpoints; unavailable or unrecorded observations show missing counts and a status. The single-row toolbar contains Top, rank, search, traffic period, App only and Pinned only. Localhost endpoints are always included. Preferences retain the 0/60/300/1800-second traffic period (default 300). Received/Sent columns accompany the live rates. Overall interval byte totals extend the existing unfiltered activity-tab summary. No summary footer is added. A disabled traffic collector falls back to TCP ranking without changing the saved throughput choice; the existing enable link opens Network settings. Selection and row objects survive ordinary refreshes. Icons use `ProcessIconProvider` and traffic history uses the existing graph renderer. The Connections action bar shares the 54-DIP minimum height of Processes and Services. It has only a name and one ellipsized summary line (identity plus cumulative totals); full traffic details live in the summary tooltip and Properties. The collapsed strip uses that same single-line summary.

Enabled traffic is indexed once per refresh by strict Windows lifetime identity and executable path. Executable rates/totals include known members independently of endpoint filters, and selection shows the executable or process owner summary. Disabled mode skips traffic indexing and hides receive/send columns. The enabled app table fits the minimum window width; its header viewport remains synchronized if an unusually narrow embedded control needs horizontal scrolling. Known observed totals remain visible when collection is unavailable; current rates become dashes. Retained-only lifetimes contribute bytes but not stale rates, while recently exited lifetimes still present in the service window can contribute rates. The session and owner metadata are bounded at 8,192 lifetimes; unmetered metadata expires after 30 seconds, while known metered metadata remains for session totals. Capacity/overflow is marked incomplete. The service also bounds PID tombstones at 8,192 entries: evicting a marker strictly older than its 30-second retention window does not mark a coverage gap or suppress rates. Evicting recent history or rejecting a lifetime at capacity retains the incomplete/capacity flags and rate-window suppression. The first observation of each lifetime establishes its baseline. Repeated snapshots do not recount bytes; per-subscription sequence IDs distinguish a real gap from another client's requests. A new generation or subscription rebases counters without discarding already observed totals. A snapshot older than three seconds is unavailable; initial/gap windows wait until the service event window starts after the baseline/gap. Sticky coverage uncertainty does not continually suppress known fresh rates. These values are never placed in persisted resource history, restart snapshots or CSV.

Connections uses a localized setup strip below the filters when process traffic monitoring is disabled in supported live desktop views. The existing settings-request event opens Network settings. The strip collapses for enabled monitoring, historical samples and Store builds; below 640 DIPs its button moves below the wrapping text. AccentButtonText uses black or white with at least 4.5:1 contrast against the current UI accent, or system highlight text in high contrast. Connections smoke captures the disabled strip in Dark, Light, Smoked Sapphire and minimum-width German layouts and checks placement, button contrast and focus.

Received and Sent ranking uses ConnectionTrafficTotals for the selected period and the same lifetime membership as the displayed byte columns. Missing totals sort last. The new enum values are appended as 4 and 5 to preserve existing saved choices; all traffic sorts fall back to TCP count while monitoring is disabled and restore when enabled.

Connections uses a 798-DIP enabled-network row minimum (780-DIP header plus the existing 18-DIP allowance) to fit the 836-DIP minimum window. History is 100 DIPs, rates 80 each, byte totals 82 each and protocol counts 44 each; app identity takes the remaining width.

Connections row history reuses `CpuGraph` with the network accent and a shared receive-plus-send scale over the selected traffic period. `ConnectionGraphData` builds it from retained `ConnectionCapture` traffic and lifetime-aware owner metadata, ending at the displayed sample; it does not substitute current traffic into Capture history. `ConnectionTrafficTotals` differences client-session counters per Windows lifetime between the first usable retained capture inside the requested period and the displayed capture. Since start uses the displayed cumulative counters. New lifetimes contribute their observed session counters; duplicate lifetimes count once. Counter resets, missing/short history and collection gaps are marked incomplete, with coverage in tooltips and ≈ on values. Missing endpoint captures never substitute live byte totals. The tab totals include retained exited lifetimes and do not follow view filters. Missing, warming-up, and unavailable rates stay gaps. Rows aggregate each executable per historical sample, with lifetime identity fallback for unknown paths. The UI benchmark also measures unpinned and pinned rows after 121 recorded traffic captures, subject to the existing capture entry budget.

TCP states outside the documented 1–12 range are unavailable, not inferred. This Windows installation has returned state 0 for a listener and inconsistent valid states for a working loopback pair. Unspecified zero-port peers are omitted; nonzero peers are preserved independently of state. The smoke proves the TCP connection with a byte exchange, checks TCP/UDP ownership and peer endpoints, and records OS-reported states without asserting that Windows must report Established. Its elevation and availability evidence is in `native-connections.json`. Fixture screenshots exercise executable rows, pins, summaries, global totals, Properties and navigation separately from native readings.

Window placement recovery lives in `MainWindow.Position.cs` and `WindowPosition.cs`. Native move/resize completion and Windows-key placement record the user's monitor and offset in physical pixels; automatic Windows relocations do not overwrite that target. Display changes and resume restart a three-second dispatcher timer. Recovery preserves focus and size, defers minimized/maximized windows until they return to Normal, and retains a missing monitor's target until the user moves the window. Monitor identity and offsets are session-only; startup continues to use the persisted bounds. Mixed-DPI visibility checks use `GetWindowRect`, matching the physical coordinates from `Screen.WorkingArea`.

Palettes whose single set lost its character under that adjustment have separate dark and light sets in `ChartPalettes.Colors`, chosen to clear 3.5:1 on every plot in their mode; `ChartPaletteTests` keeps those sets unadjusted, and checks that Colorblind, Signal, High-Contrast & Inclusive, Copper and Gunmetal keep every pair of resources at least CIE76 ΔE 15 apart under simulated deuteranopia and protanopia, and 10 under tritanopia. Settings swatches show chart colors, and the six-resource Appearance preview uses both shades; Windows high contrast mode uses system brushes instead.

Copper's brushed reflection is included in the contrast test. `CpuGraph` shapes its axis, network-scale and selected-sample labels at 12 DIPs and measures alternate-view label widths at that same size.

Settings has separate Monitoring and Network sidebar pages. Monitoring contains history retention, restart history, the gauge peak window and disk selection; Network contains adapter selection and per-process monitoring/service controls. Both retain pending edits while navigating and share Save/Cancel. Applying a process-network change selects Network before showing progress or an error. The capture smoke checks that Appearance, Monitoring and Network do not scroll at full designed height in Dark and Light themes.

`SettingsWindow.Field` gives dropdown rows two equal star columns, so each selector takes half the content width; long selected network names remain available through the selector tooltip. Field labels trim when needed at the minimum window width.

Rules for new code:

- **`MonCore` is portable.** It references no WPF, Windows Forms, Avalonia, System.Management or native imports. `AssemblyBoundaryTests` checks assembly references and imports, and `MonitoringLayerTests` checks compiled type use.
- **The Windows adapter depends on MonCore.** WinMon references both projects. `MonCore.Tests` references only MonCore; `MonCore.Windows.Tests` references the adapter.
- **Sampling lives outside the window.** `MonitorSession` owns the capture loop, the queue and history. It reaches the UI thread through a `post` delegate the window supplies.
- **Capabilities and observations are separate.** `IFrameSource.Capabilities` says which system and process metrics and actions an implementation supports. Nullable readings still report per-sample unavailability, and process actions recheck the lifetime and Windows permission at execution.
- **A view is a UserControl updated through one `Update(...)` call.** It raises events when the user changes something; the window keeps persisted settings in `MonitorPreferences` and passes them back in.
- **XAML for layout and window chrome; code-built elements only for rows updated every tick.**
- **Diagnostics and the benchmark use internal members, never reflection on WinMon's private names.** When one needs more, add a named member to `MainWindow.Internal.cs` or the view.
- **Structural changes must not regress performance.** Measure before and after as described under [Performance](#performance).

## Measurement semantics

### Resources

- **Logical processors** adds a CPU-only grid to the existing chart dropdown. Each processor's utilization is `(kernel + user − idle) / (kernel + user)` over successive Windows [SystemProcessorPerformanceInformation](https://learn.microsoft.com/windows/win32/api/winternl/nf-winternl-ntquerysysteminformation#parameters) readings, on its own 0–100% scale. Kernel includes idle. The machine and process percentages keep their existing total-capacity denominator. A missing or invalid processor reading breaks that processor's trace; an optional per-processor query failure leaves total/process CPU sampling intact. Grid cells share the selected chart range and historical interval. Processor count changes require a fresh baseline. Short cells use labeled sparklines, with values in tooltips and UI Automation; larger cells also display a percentage and grid guides.
- CPU, memory, disk and GPU traces use a fixed 0–100% scale; network throughput uses its own visible-peak scale.
- The chart toolbar keeps Auto immediately after the centered Live/Capture switch, without shifting that switch; the 150-DIP chart type selector stays on the left and time ranges stay on the right. Its width accommodates Logical processors; longer translations remain available in the tooltip. The former "2m peak" legend and tooltip are absent. The gauge setting explains the dark peak mark and its configurable window.
- Resource gauges in Full and Compact views are drawn by `MetricGauge` in the `GaugeStyle` chosen in Settings (default Bowl). Each gauge shows the live level and a dark peak line. GaugePeakWindowSeconds selects 60, 120 (default), 300 or 600 elapsed seconds, independently of chart range. Peaks retain the newest maximum sample, skip gaps and invalid readings, match configured disk volumes and keep network readings on the latest adapter. Only retained samples contribute; a shortened history can cover less than the requested window. Full-view tiles use symmetric horizontal margins so each bowl and value share the center of their column. Arc styles put a decorative peak-marker icon and value beside CPU, memory, disk and GPU names at every width; the accessibility name and tooltip retain the Peak label. Peak labels always use RAM used, disk throughput or dedicated GPU memory from the utilization-peak sample when available, otherwise a percentage. It does not change live readings. The shared resource tooltip includes the peak, its local timestamp and age relative to the latest sample, with monotonic elapsed time where available; it is available on the tile, corner and keyboard focus in both views. MetricDetails formats that section only while open. `MetricReadout` accounts for each tile's outer margin to place the corner label 12 DIPs from its right edge. The network gauge displays received bytes per second on its own peak-window auto scale, which matches the chart when both ranges agree; arc styles print the download peak (`RateText.Short`, such as "8MB/s") with the peak icon; the tooltip prints the full rate and top of the automatic scale. Percentages use 0–100. An unavailable current reading hides its gauge and corner label. Every style fits `MetricReadout.LayoutHeight`; see [Gauge styles](design/GAUGE-STYLES.md) for the layouts.
- **Memory** is used over total OS-visible physical RAM, with GiB readouts.
- **Disk** is active time (`100 − % Idle Time`) on each configured volume, with read/write throughput in decimal MB/s. It is not space used. Drive letters identify logical volumes, which may share a physical disk, so disk percentages are never added together.
- **Network** measures one connected Ethernet or Wi-Fi adapter. Automatic selection prefers one with a gateway, then the fastest, and keeps that choice while it stays connected. Network settings can instead hold a specific adapter ID; if it is disconnected or missing, readings stay unavailable rather than switching adapters. Adapters are re-enumerated after a Windows network-change event or every 30 seconds; counters are read every second. Changing the selected adapter resets rate and total baselines. Traffic readouts use adaptive decimal KB/s, MB/s or GB/s, while adapter link speeds in resource details and hardware inventory retain Mbps/Gbps. The gauge leads with receive and shows send below; utilization uses the busier direction over the reported link speed. Graph scales and samples remain bit-based internally. Automatic capture thresholds display MB/s and convert to/from the existing stored Mbps values, preserving saved rule behavior. Connections totals and owner details explain the five-second averaging window ending normally three seconds behind the current time in their tooltip and accessible text. This is link utilization, not Internet bandwidth.
- **GPU** reports the busiest physical engine across adapters, from the Windows GPU Engine performance counters, without vendor libraries. Process contributions are summed within each engine before the busiest is chosen; independent engines and GPUs are never added. Live VRAM use and temperature are out of scope; Info shows dedicated memory capacity.
- Interface or speed changes, counter resets, startup and long collection gaps need fresh rate baselines. The received and sent totals restart only when the adapter changes or its counters go backwards. Unavailable metrics show a dash and break the trace. A CPU provider failure does not stop the other resources. A capture that fails, or a sampler that cannot start, shows readings unavailable and is retried each second.
- Machines with more than one active processor group are unsupported and show unavailable CPU readings rather than partial machine totals; an update there proves healthy from the other resources.

Automatic capture report writes are tracked on the UI thread. Normal close and in-app update restart wait for them, like CSV exports and process dumps, before closing the window or committing the update. The capture smoke includes a delayed-write shutdown check in `captures.json`. A stalled report destination can delay exit; forced termination and Windows session shutdown do not provide this asynchronous wait.

Invalid JSON settings whose backup fails remain protected: subsequent saves retry the backup and fail without replacing the original until it succeeds.

### Processes

Portable lifetime, executable equality and CPU availability contracts are described in [Portable process identity](design/PORTABLE-PROCESS-IDENTITY.md). Windows defaults and history format 1 remain unchanged; portable consumers use `ObservedCpuPercent` and explicitly select their identity policy.

- Process CPU is a share of total machine CPU capacity, not per core or lifetime. CPU, GPU and I/O columns use a five-second window.
- The list ranks by CPU, GPU, Memory, I/O, Threads or Handles (`ProcessSort`). Memory, Threads and Handles rank the latest observation of processes in the newest sample.
- **Memory** is the resident working set, including shared pages. **Grouped** rows instead sum the private bytes of current members, since working sets share pages.
- Processes and Services keep units in numeric cells: CPU/GPU percentages, memory in adaptive binary B/KiB/MiB/GiB/TiB and read/write I/O rates in adaptive decimal B/KB/MB/GB/TB per second. Scaled memory and I/O values use one decimal place; bytes use whole numbers. Their headers use metric names only; Services labels private-memory totals as Memory. Usage already keeps Share's percent sign and adaptive decimal byte units in its cells.
- **GPU** per process is its busiest engine per interval, averaged over readable intervals. A missing counter or unverified process lifetime shows a dash. Per-process GPU is not additive, so a group shows its busiest member and the Other processes GPU cell is a dash.
- **I/O** is interval read/write MB/s and includes file, network and device operations; it is not disk-only.
- Grouping identifies executables by full path, falling back to the process name when the path cannot be read.
- Sparklines plot one-second values of the ranking metric over the last two minutes, on one shared scale across rows (zero to the busiest listed row's visible peak with headroom).
- Listed rows plus Other processes need not sum to the machine total. The Process column heading reports the unattributed remainder, and very short-lived processes can exit between polls.

### Collection and history

- Restart-history format 3 includes nullable per-logical-processor readings. Formats 1 and 2 still load, with those readings unavailable; older builds cannot restore format-3 history. Normal restarts and update restarts use the same versioned sample encoding.
- MonCore's `MonitorSession` owns history, latest samples, usage and service frames on the thread selected by the caller's `post` delegate. The collection loop runs on the thread pool, enqueues captures in order and never waits for the UI to drain them. Call session state operations on the dispatch thread; cancellation ends collection and `Close()` discards later drains.
- `ProcessUsage.CreationTicks` remains Windows FILETIME in the current Windows collector and saved-history format. A portable lifetime/start-time model is required before a macOS collector writes samples or persistence. Group keys currently compare executable paths without case, preserving WinMon behavior.
- CPU percentages are shares of total machine capacity; I/O rates use bytes per second, GPU is the busiest engine, and unavailable readings stay null. `WorkingSetBytes` is resident memory and `PrivateBytes` is private committed memory; a macOS footprint needs its own measurement contract.
- All processes come from one `NtQuerySystemInformation(SystemProcessInformation)` call, without opening process handles, so access-restricted processes are measured too. The buffer is pinned and reused, and collection stops at 20,000 processes, counting any beyond.
- Collection is sequential within one pass, not an atomic snapshot across Windows APIs.
- `ProcessRetention.Compact` keeps, in each retained sample, the processes with CPU, I/O or GPU readings, processes that have shown an app window, pinned processes, and the 50 largest working sets, thread counts and handle counts (ties at the cut-off are all kept). Dropped entries are counted in `CompactedProcesses`, and averages treat them as zero.
- `MonitorHistory` holds up to a 500,000-process-entry budget; the UI reports when that shortens the retention window. Service history keeps up to two minutes under its own bound.
- History is in memory by default. In-app updates save it for the new version to restore; see [the design note](design/UPDATE-RESTART-HISTORY.md). The optional normal-restart snapshot saves compacted samples beside settings, then consumes the file on startup before sampling. It rebases historical monotonic timestamps onto the current process clock and shifts live samples by the same offset when needed after a reboot. Usage totals and service frames are not included; see [the normal-restart design](design/NORMAL-RESTART-HISTORY.md).

## Implementation notes

- **Preferences** are saved atomically to `%LOCALAPPDATA%\WinMon\settings.json`. With an empty `portable.flag` beside `WinMon.exe`, they are loaded and saved beside the executable instead, whatever the working directory, with no fallback if that folder is not writable. Enums are stored by name through `LenientEnumConverter`, which reads a name this build lacks (one a newer build added) as an undefined value for `Validate` to replace, so only that setting resets. A file that still cannot be parsed, or stays locked after five tries, is copied to `settings.invalid.json` before the defaults are used, because the next save overwrites it.
- **Hardware Info** uses Windows [installed-memory reporting](https://learn.microsoft.com/windows/win32/api/sysinfoapi/nf-sysinfoapi-getphysicallyinstalledsystemmemory) and [DXGI adapter descriptions](https://learn.microsoft.com/windows/win32/api/dxgi/ns-dxgi-dxgi_adapter_desc1). The detailed sections use System.Management with read-only [processor](https://learn.microsoft.com/windows/win32/cimwin32prov/win32-processor), [memory](https://learn.microsoft.com/windows/win32/cimwin32prov/win32-physicalmemory) and [storage](https://learn.microsoft.com/windows-hardware/drivers/storage/msft-disk) queries, finite enumeration waits and explicit disposal. The tabbed Info window uses XAML for layout, guide expanders and About, and code only for snapshot rows. Inventory runs only when Info is opened or refreshed; tab changes do not collect again. Copy includes collapsed details. Guide has nine feature-oriented expanders, each with a purpose and two steps, including a CPU-spike walkthrough. Steps use the `GuideStep` style (number badge, optional `ButtonIcon`, text), and Charts adds a text-free XAML diagram drawn with theme brushes. Each topic's Show me button carries a topic Tag; Info closes with `ShowMeTopic`, and `MainWindow.ShowGuideTarget` leaves Compact view, opens the needed panel or tab, focuses the target and flashes it unless Windows animations are off. Feature smoke fails if any topic's Tag has no `GuideTarget`, and scrolls each expanded topic into view for Dark/Light captures (`guide-*.png`). Guide text describes current behavior; About shares the owner's checker, busy state and update offer. Update now closes Info before the existing download/restart flow, and Store builds show a Store-managed explanation without GitHub controls. A drive's media type is associated with an OS disk only when identifiers match unambiguously.
- **Ending a process** uses [TerminateProcess](https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess) after checking the creation time against the same handle, so a reused PID cannot be targeted, and refuses [critical processes](https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-isprocesscritical). Group termination checks each member separately and collects failures. Historical, system and WinMon rows are disabled, and nothing elevates.
- **Pins** live in `src/MonCore/Monitoring/ProcessPins.cs` and persist as `SavedProcessPin` entries in `MonitorPreferences.PinnedProcesses`. Individual pins use PID plus creation time; grouped pins use the grouping key, with separate lists for each mode. The view publishes immutable retention predicates to the sampling thread so pinned processes survive compaction. Ranked rows exclude pinned identities before applying Top N and the remainder.
- **Compact view** (`MainWindow.Compact.cs`) is a 142-DIP window with the existing title bar and six `MetricReadout` instances. They copy the full readouts' live text and receive the same gauge values, configured-window peaks and selected style. The second disk is shown only when a drive is configured. Resource names replace chart-series checkboxes; chart visibility preferences remain unchanged. `CompactMode` persists separately from the full-view size. `StartupView` chooses whether launch uses that last saved mode or forces Full or Compact; it does not prevent switching views later. Ctrl+F restores the full view before focusing process search.
- **Activity panel** (`MainWindow.ActivityPanel.cs`) keeps its tabs and counts when collapsed, hiding only the body and resize divider. `ActivityPanelCollapsed` and `ActivityPanelRatio` persist the disclosure state and expanded star-size ratio. Collapse, entry to Compact view and normal/session-end exit capture the latest split; collapsed or Compact layouts never overwrite it. Expansion restores the split within the existing row minimums. Clicking any tab or using Ctrl+F expands the body. Views remain alive and monitoring continues.

- **Chart panel** shares the activity panel's disclosure control and split handling. `ChartPanelCollapsed` persists independently; the plot and snapshot share `ChartBody`, while chart selectors and the restore chevron remain visible. Changing the chart type or period or clicking Live/Capture expands the chart; rebuilding selectors preserves its collapsed state. Either collapsed body hides the divider, and neither collapsed layout overwrites the saved split. The feature smoke includes chart collapse, focus recovery, both panels collapsed, Compact view, persistence and split restoration (`chart-panel-*.png`).
- **Services**: see [the services implementation note](design/services-implementation.md). The activity tab strip counts individual services in the selected service frame, including services in shared hosts; Running means state 4. An unavailable frame shows dashes. Usage counts ledger app groups, with Active meaning at least one currently running process; its totals continue to update while a capture is selected.
  Service pins persist case-insensitive SCM names, independently of host lifetimes. Matching pinned groups precede the ranked Top limit in pin order and appear once even when several members are pinned. Shared-host pin buttons toggle all current member names; individual service children toggle only their own name. Search/status filters apply to both sections, and the saved Pinned only choice excludes ranked groups. Missing names remain saved without synthesizing observations. [Service pins](design/SERVICE-PINS.md) records the interaction and verification scope.

Connections places its localized saved-pin count in the first column header, using the Processes dot separator and pin accent. The first unpinned row displays the localized ranking divider when visible pins precede it; Pinned only and filters suppress it when no split remains. Populated lists show collection notices through the column-header tooltip; empty/error notices retain their footer. The static UDP explanatory footer is removed. The Connections smoke checks pinned-header bounds at normal and narrow German widths.

Full-view section headers occupy the full-width layout grid. Gauges keep 20-DIP side margins and the chart 8-DIP margins; activity views use 8-DIP gutter columns and span their toolbar backgrounds across all three columns. Keep header backgrounds inside their parent bounds: negative margins are clipped horizontally when short windows force WPF to clip overflowing row minimums. The feature smoke checks header width and ancestor layout clips at 900, 720 and 600 DIPs high for all three activity tabs.

The update-footer smoke checks that the footer avoids the process list when the layout rows fit the available height. On smaller desktops, row minimums can overflow even at the initial window size; the footer intentionally overlays the bottom there. Footer visibility is also checked at 300 DIPs and the minimum window height.

WinMon samples once a second all day, so its own cost is a feature. Measure structural or hot-path changes before and after, and add the results to the top of the [performance history](PERFORMANCE-HISTORY.md).

### Benchmark the UI thread

`tools/WinMon.Performance` drives the real window with synthetic 850-process samples while sampling is stopped. Each scenario runs 400 warm-up frames, then seven batches of 60, and reports UI-thread time, allocation and a pixel hash of the rendered window. Scenarios: live, historical, grouped, Services, compact, pinned and selected (individual and grouped), an open CPU tooltip, `UsageLedger.Add`, and 60-minute update and normal-restart history saves and reads. A 12-logical-processor grid with pinned/selected processes runs after the existing pixel capture, so it does not shift the earlier scenarios' synthetic sample sequence. The Connections scenarios keep that chart and use 60 processes and 480 TCP endpoints: executable rows. Those original cases leave per-process monitoring disabled. Additional cases apply synthetic per-process network readings and retained traffic history, including five pins. They measure UI refresh only, with native collection disabled. Pixel capture clears keyboard focus and checks that it remains clear, avoiding incidental button focus outlines. Synthetic samples also carry per-processor readings into the history-save workload.

```powershell
dotnet build tools/WinMon.Performance/WinMon.Performance.csproj -c Release -m:1 -p:UseSharedCompilation=false
./tools/WinMon.Performance/bin/Release/net10.0-windows/win-x64/WinMon.Performance.exe "$PWD/artifacts/bench.json" "$PWD/artifacts/bench.png"
```

- Build a baseline from `main` before editing, and keep its output folder so it stays runnable.
- Alternate baseline and changed runs on a quiet machine, at least four of each, and compare medians. An IDE indexing in the background hides real differences.
- Pixel hashes should match the baseline. The window is on screen, so a pointer over it can produce a known alternate frame.
- The first scenario is sensitive to JIT tiering. If only it differs, rerun both builds with `DOTNET_TieredCompilation=0` to tell tiering from extra work.

### Profile the whole app

`--profile-output <dir> [seconds]` runs the real window and sampler in isolation, waits 20 seconds, then measures for the given duration (default 60, 10–3600). It writes `profile.json` with CPU per second, working set, private bytes, managed heap, allocation rate, GC counts and retained process entries, reading memory for this process only. Run both builds side by side and swap launch order, because the first-launched instance tends to use more UI-thread time. Run at least 150 seconds when service history matters, so it reaches its two-minute steady state.

### Where the time goes

As of October 2026 (see the [history](PERFORMANCE-HISTORY.md#chart-drawing-and-refresh-october-22-2026)):

- The process snapshot dominates sampling, and its cost follows the machine's thread count, because the query returns every thread. It is the OS floor for 1 Hz sampling.
- On the UI thread, WPF text formatting and layout of values that actually changed is about half of a live frame; WinMon's own refresh and chart drawing are the rest.
- Whole-app CPU barely moves with UI-thread savings. Allocation and private bytes are the more sensitive measures.

### Decisions in force

| Decision | Why |
| --- | --- |
| Gen0 budget capped at 6 MiB | Private bytes 86 → 52 MiB in a 60 s profile, for cheap extra gen0 collections |
| Single-file compression off | About 130 MiB less working set and faster startup |
| Default tiered PGO kept | Turning it off cuts launch CPU but only breaks even after about an hour |
| No ReadyToRun | Most tier-1 work is already-precompiled WPF code; +20 MB for little gain |
| Retain only active, app, pinned and largest processes | About 87% fewer retained process entries at 10 minutes |

Release packaging tests `WinMon.sln`, covering all six test projects, and writes separately named TRX results per test run.

### Services and Connections CSV
